# PROMPT MESTRE — ATUALIZAÇÃO DO WORKFLOW N8N DO PETFLOW

Você está trabalhando na atualização de um **workflow n8n já existente** responsável pelo atendimento de uma loja de pet shop através do WhatsApp.

A infraestrutura atual já utiliza:

* **n8n** para automação/orquestração;
* **Evolution API** para integração com WhatsApp;
* **Supabase** para banco de dados;
* Sistema/site/app próprio para gerenciamento das lojas, clientes, pets, serviços, funcionários e agendamentos.

## OBJETIVO

Sua tarefa é **analisar o workflow existente e aprimorá-lo**, implementando as regras de negócio descritas neste documento.

### REGRA FUNDAMENTAL

**NÃO recrie o sistema do zero.**

Primeiro analise completamente o workflow atual.

Identifique o que já funciona.

Preserve o que já funciona.

Reutilize os nós existentes sempre que possível.

Modifique somente o necessário.

Crie novos nós somente quando realmente necessário.

---

# 1. ARQUITETURA: APENAS UM WORKFLOW

Esta é uma exigência do projeto:

## TODO o atendimento deve permanecer em UM ÚNICO WORKFLOW n8n.

Não criar workflows separados para:

* atendimento;
* cadastro;
* agendamento;
* confirmação;
* cancelamento;
* serviços;
* preços;
* lembretes;
* atualização de status;
* seleção de loja;
* notificações.

Tudo deverá permanecer dentro do workflow principal.

É permitido utilizar diferentes gatilhos dentro do mesmo workflow quando necessário.

Por exemplo:

```text
                    WORKFLOW PETFLOW
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
     Webhook Evolution API      Schedule Trigger
             │                         │
             ▼                         ▼
       Atendimento                 Lembretes
             │                         │
             └────────────┬────────────┘
                          ▼
                       SUPABASE
```

Continua sendo um único workflow.

Antes de modificar o workflow:

6. Identifique os updates.

13. Identifique como as mensagens são enviadas.
14. Identifique qualquer lógica de lembrete existente.
15. Identifique qualquer lógica de status existente.

Depois dessa análise, determine quais partes podem ser reutilizadas.

### NÃO faça:

* duplicação desnecessária de nós;
* criação de consultas que já existem;
* substituição de integrações funcionando;
* criação de workflows adicionais;

# 4. REGRA DE MÚLTIPLAS LOJAS

Um mesmo número de WhatsApp pode estar vinculado a:

* uma loja;
* várias lojas.

## UMA LOJA

Se o número estiver relacionado a apenas uma loja:

```text
telefone
↓
consulta lojas
↓
1 resultado
↓
selecionar automaticamente
↓
salvar store_id
```

Não perguntar novamente qual loja.

---

## VÁRIAS LOJAS

Se o número estiver relacionado a mais de uma loja:

```text
telefone
↓
consulta lojas
↓
mais de uma loja
↓
perguntar qual loja
↓
cliente escolhe
↓
validar escolha
↓
salvar store_id
↓
continuar atendimento
```

Exemplo:

> Olá! 😊
>
> Encontrei mais de uma loja vinculada a este número.
>
> Qual loja você deseja acessar?
>
> 1️⃣ Pet Shop Centro
> 2️⃣ Pet Shop Pituba
> 3️⃣ Pet Shop Paralela

A seleção deverá ser salva no contexto da conversa.

# 5. ISOLAMENTO TOTAL POR LOJA

Essa é uma das regras mais importantes de todo o sistema.

Depois que o cliente selecionar uma loja, **todas as operações deverão utilizar essa loja como contexto**.

A informação principal será:

```text
store_id
```

Todas as consultas deverão respeitar a loja selecionada.

Isso inclui:

* cliente;
* pet;
* serviços;
* preços;
* funcionários;
* horários;
* disponibilidade;
* tempo de espera;
* agendamentos;
* configurações;
* regras;
* status;
* informações da loja.

Nunca misturar dados entre lojas.

# 7. SUPABASE COMO FONTE DA VERDADE

O Supabase/sistema será a fonte oficial dos dados.

O n8n deve consultar os dados reais antes de responder.

A IA nunca deve ser considerada fonte oficial de informação.

Exemplo:

```text
SUPABASE
   ↓
Preço real
   ↓
n8n
   ↓
IA
   ↓
Resposta
```

Nunca:

```text
Cliente
↓
IA
↓
IA inventa preço
```

---

# 8. CONSULTAS ANTES DA IA

Esta é uma regra obrigatória.

Sempre que uma informação puder ser obtida do sistema, ela deverá ser consultada **ANTES do nó do agente de IA**.

Exemplo:

Cliente:

> Quanto custa o banho?

Fluxo:

```text
Mensagem
↓
Identificar loja
↓
Consultar serviço
↓
Consultar preço
↓
Obter resultado real
↓
Enviar somente resultado necessário para IA
↓
IA humaniza resposta
↓
Evolution API
```

---

# 9. REDUÇÃO DE TOKENS

O agente de IA deve receber somente as informações necessárias.

Não enviar:

* JSON gigante;
* tabelas inteiras;
* dados de outras lojas;
* histórico desnecessário;
* informações duplicadas;
* dados que não têm relação com a pergunta.

Exemplo:

Em vez de enviar centenas de campos:

```json
{
  "store": "...",
  "services": "...",
  "employees": "...",
  "customers": "..."
}
```

Enviar apenas:

```json
{
  "store": "Pet Shop Centro",
  "intent": "consulta_preco",
  "service": "Banho",
  "price": 50
}
```

---

# 10. AGENTE DE IA

O agente de IA terá uma função específica:

## HUMANIZAR A COMUNICAÇÃO.

Ele deverá:

* interpretar o contexto;
* organizar a resposta;
* deixar a mensagem natural;
* ser simpático;
* utilizar linguagem simples;
* utilizar pequenos parágrafos;
* utilizar emojis com moderação;
* evitar respostas robóticas.

A IA não deverá tomar decisões de negócio que dependam do banco.

---

# 11. PROIBIÇÃO DE INVENTAR INFORMAÇÕES

A IA nunca poderá inventar:

* preços;
* serviços;
* horários;
* funcionários;
* disponibilidade;
* tempo de espera;
* horário de funcionamento;
* dados de clientes;
* dados de pets;
* agendamentos;
* confirmações;
* cancelamentos;
* políticas.

Se a informação não estiver disponível:

**não inventar.**

Exemplo:

> "Vou verificar essa informação para você. 😊"

Ou:

> "Não encontrei essa informação disponível no momento."

---

# 12. REGRA DE CONFLITO

Se a IA receber uma informação diferente da informação retornada pelo sistema:

**O SISTEMA SEMPRE VENCE.**

Exemplo:

Sistema:

```text
Preço = R$ 70
```

A IA deverá informar:

```text
R$ 70
```

mesmo que seu conhecimento ou contexto anterior indique outro valor.

# 13. CADASTRO DO CLIENTE

Quando o cliente não estiver cadastrado:

```text
Consultar cliente
↓
Não encontrado
↓
Perguntar se deseja cadastrar
```

Exemplo:

> Ainda não encontrei seu cadastro por aqui. 😊
>
> Quer fazer seu cadastro para continuarmos?

Se aceitar:

```text
Coletar dados necessários
↓
Validar
↓
Enviar para Supabase/API
↓
Verificar resposta
↓
Somente se sucesso:
continuar atendimento
```

Não considerar cadastro concluído sem confirmação do sistema.

---

# 14. PETS

Um cliente pode possuir vários pets.

Consultar os pets relacionados ao:

```text
customer_id
+
store_id
```

Se houver vários:

> Qual pet você gostaria de agendar? 🐶🐱
>
> 1️⃣ Thor
> 2️⃣ Mel
> 3️⃣ Nina

Salvar o `pet_id` escolhido no contexto.

---

# 15. SERVIÇOS

Consultar serviços da loja selecionada.

Sempre utilizar:

```text
store_id
```

O agente de IA não pode criar ou sugerir serviços que não estejam no retorno da consulta.

---

# 16. PREÇOS

Os preços deverão ser consultados diretamente no sistema.

Nunca permitir que a IA estime valores.

Se o preço depender de:

* porte;
* raça;
* peso;
* tamanho;
* serviço;
* pet;
* funcionário;
* horário;

consultar as regras existentes antes de enviar a informação para IA.

---

# 17. FUNCIONÁRIOS

Funcionários devem ser consultados exclusivamente dentro da loja selecionada.

Nunca apresentar funcionários pertencentes a outra loja.

---

# 18. HORÁRIO DE FUNCIONAMENTO

Consultar os horários reais da loja.

A IA não pode assumir:

> "A loja funciona das 8h às 18h."

a menos que o sistema tenha retornado essa informação.

---

# 19. DISPONIBILIDADE E TEMPO DE ESPERA

Quando o cliente perguntar sobre:

* horário disponível;
* fila;
* tempo de espera;
* disponibilidade;
* próximo horário;

consultar o sistema primeiro.

Somente o resultado real poderá ser enviado ao cliente.

# 21. NUNCA CONFIRMAR AGENDAMENTO SEM CONFIRMAÇÃO REAL

Essa regra é obrigatória.

Se o sistema retornar:

```text

```

> Seu agendamento está confirmado.

Deve responder algo como:

> Prontinho! 😊
>
> Enviei sua solicitação para a loja.
>
> Assim que o agendamento for confirmado, aviso você por aqui. 💙

Somente se o sistema retornar:

```text
CONFIRMED
```

poderá informar:

> Tudo certo! 🐶💙
>
> Seu agendamento foi confirmado!

# 28. EVOLUTION API

A integração atual com a Evolution API deverá ser preservada.

Antes de modificar qualquer nó da Evolution:

1. verificar como ele funciona;
2. verificar payload;
3. verificar autenticação;
4. verificar URL;
5. verificar instância;
6. verificar tratamento de erro.

Não substituir uma integração funcionando sem necessidade.

---

# 29. TRATAMENTO DE ERROS

Se o Supabase/API falhar:

Não informar que a operação foi concluída.

Exemplo:

> Tive um probleminha para consultar o sistema agora. 😕
>
> Pode tentar novamente em alguns instantes?

Se o cadastro falhar:

Não dizer que o cadastro foi realizado.

Se o agendamento falhar:

Não dizer que foi agendado.

Se a confirmação não existir:

Não dizer que está confirmado.

# 33. REGRA DE DECISÃO

A IA não deve decidir se uma operação foi realizada.

Quem determina isso é o resultado da operação.

Exemplo:

```text
SUPABASE/API
       ↓
status = success
       ↓
n8n
       ↓
IA
       ↓
"Cadastro realizado com sucesso."
```

Mas:

```text
SUPABASE/API
       ↓
status = error
       ↓
n8n
       ↓
IA
       ↓
"Não consegui concluir seu cadastro neste momento."
```

---

# 34. ESTRUTURA DE DECISÃO

* IF;
